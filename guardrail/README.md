# 리뷰어3 모델 비교 — 1단계: 평가 데이터 준비

현재 단계는 **데이터 후보 작성과 오염 검사**다. 모델 추론·학습·F1/latency 측정은 실행하지 않았다.

## 파일과 상태

- `eval.candidate.jsonl`: AI가 새로 작성한 합성 후보 24개. 정상 12개, 인젝션·탈옥·시스템 프롬프트 추출 각 4개. 한국어/영어 각 12개.
- `REVIEW.md`: ID별 문장, 예상 라벨, 근거를 사람이 확인하는 검토표.
- `data_manifest.json`: 후보와 배제 코퍼스의 SHA-256, 원본 파일 해시·출처, 기준 커밋.
- `provenance/exclusion_corpus.jsonl`: 기존 프로젝트에서 이미 사용·노출된 텍스트 138개를 합친 배제 스냅샷.
- `validate_data.py`: Python 3.9+ 표준 라이브러리만 사용하는 검사기. 설치나 모델 다운로드가 없다.

**24개 모두 `review_status=pending`이다. 아직 `eval.jsonl`은 만들지 않았다.** 사람 확인과 최종 해시 고정 뒤에만 최종 평가 입력으로 승격한다. 테스트의 가상 승인 메타데이터는 메모리 안에서만 쓰며 실제 후보를 승인하지 않는다.

## 이번 평가의 의미

정답 `benign`을 0, 나머지 세 라벨을 1로 매핑하는 **입력 텍스트의 악성 여부** 평가다. 정책 엔진 차단 여부나 과거 공격 성공 여부를 정답으로 쓰지 않는다. 인용된 공격 문구의 분석, 공개 프롬프트 문구 편집, 무해한 역할극, 공개 문자열 인코딩은 정상 사례다. GLiNER 출력 span 평가와 agent ASR은 별도 실습이다.

현재 후보는 정상/공격을 12/12로 맞춘 소형 합성 자료다. 실제 서비스의 공격 비율을 반영하지 않으며, 한국어/영어 쌍이 같은 원본에 속하므로 24개의 독립 출처가 아니다. 이 데이터만으로 일반화 성능·운영 성능을 주장하지 않는다.

## 출처 분리와 한계

기준 원격 커밋은 `77dc67e3ebd08f809598e25833ea66e7e1b5413a`다. 배제 코퍼스는 그 커밋의 W4 JSONL 3개, W3 공격/정상 YAML의 payload와 user_request, W2 sandbox 텍스트를 포함한다.

로컬에 남아 있던 이전 zero-shot 8개, 분류 공부용 train/validation/test 32개, span 공부용 train/validation/test 30개도 모두 배제했다. 이 후속 실습 자료는 현재 원격 main에 없는 로컬 이력 스냅샷이다. 기존 로컬 프로젝트·모델을 변경하거나 과거의 미반영 커밋을 이번 커밋에 섞지 않았다. 각 입력의 해시는 manifest에, 추출한 텍스트와 원본 위치는 배제 코퍼스에 보존했다. 배제 자료의 기존 라벨을 새 정답으로 재사용하지 않는다.

검사는 ID, 필수 필드, 라벨 enum, 비어 있는 텍스트, 동일 출처/템플릿, 정규화한 동일 문장과 유사 문장을 확인한다. Unicode NFKC·대소문자·공백·문장부호를 정규화하며, 20자 이상은 SequenceMatcher 비율 0.86 이상, 40자 이상의 포함 관계도 중복 후보로 차단한다.

이 검사는 **알려진 프로젝트 자료에 대한 기계적 검사**다. 바뀐 출처 이름만으로 독립성을 증명하지 않으며, 의미상 유사한 템플릿·번역·모델 사전학습 데이터와의 겹침은 자동으로 보장할 수 없다. 새 source_id/family_id와 라벨 근거는 사람도 검토해야 한다. 임계값을 이 평가 자료에 맞춰 조정하거나 이 자료를 학습에 사용하지 않는다.

## 직접 실행하고 기록하기

저장소 루트에서 아래 명령을 순서대로 실행한다. `python3`가 Python 3.9 이상이면 추가 패키지가 필요 없다.

```bash
python3 --version
python3 -B -m unittest -v guardrail.test_data
python3 -B -m guardrail.validate_data --mode candidate --output /tmp/r3-benchmark-data-check.json
```

성공하면 후보 검사 명령의 종료 코드는 0이고, 출력에 `schema_valid: true`, `rows: 24`, `pending_rows: 24`, `ready_for_benchmark: false`가 표시된다. 이것은 **초안 구조·중복 검사 통과**이며 사람의 라벨 승인이나 모델 평가 완료가 아니다. 원문 대신 ID와 통계를 로그로 남긴다.

다음 명령은 아직 최종 평가를 허용하지 않는지 확인하는 음성 검사다. **현재는 종료 코드 2가 정상 기대값**이다.

```bash
python3 -B -m guardrail.validate_data --mode benchmark
```

기대 메시지는 `evaluation is not reviewed and frozen`이다. 검증 실패를 우회해서 모델 평가를 실행하지 않는다.

## 사용자가 확인할 일

1. `REVIEW.md`에서 24개의 예상 라벨·근거·한국어/영어 의미를 확인한다.
2. 맞으면 채팅에서 전체 승인 의사를 알리고, 다르면 항목 ID와 수정 내용을 알려준다. 승인 전에는 assistant가 사람 검토 완료로 기입하지 않는다.
3. 확인 후 텍스트·라벨·출처·근거를 묶은 `reviewed_record_sha256`, 검토자·시간을 남긴다. 수정 시 재검토한다.
4. 최종 파일을 `eval.jsonl`로 만들고 `evaluation_sha256`, `human_review_complete`를 갱신한 뒤 benchmark 모드 검사를 통과시킨다.

그다음 단계에서 기존 GuardResult 인터페이스를 사용하는 실제 모델 평가기와 어댑터를 연결한다. 로컬에는 이전 공부용 GLiClass 학습 가중치가 있지만, 최종 비교에서 원본 zero-shot과 공부용 head 학습 버전을 구분해야 한다. 비교 모델 설치·대형 가중치 실행은 이번 단계에 포함하지 않는다.
